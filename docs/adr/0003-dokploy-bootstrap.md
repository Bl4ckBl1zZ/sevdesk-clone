# ADR 0003 — Dokploy bootstrap, deployment stack and verified CLI flags (P0)

- **Status:** accepted · 2026-10-12
- **Context:** 08 §5 sketches `deploy/bootstrap.sh` in the syntax of the generated Dokploy CLI and asks to verify every
  flag in P0 (spikes 1, 2, 7). The CLI on the dev machine is `0.30.7-server.0.41.1`, generated by
  `deploy/scripts/build-dokploy-cli.sh` from the live server (fork `Bl4ckBl1zZ/dokploy` **v0.41.1**). All checks below
  were **read-only** (`--help`, `all`/`list`/`one` queries, the server's OpenAPI document); no create/update/deploy/
  retag command was run.

Other findings:
- The CLI reads `./.env` from the working directory for `DOKPLOY_URL`/`DOKPLOY_API_KEY` (harmless; `.env*` is ignored).
- **Spike 2:** gateway status is available (`tailscale list` / `inspect-gateway --serverId`), the Service FQDN too, but
  not the TailVIP → `bootstrap.sh` resolves the FQDN via MagicDNS (`dig @100.100.100.100`) from the (tailnet) machine
  that runs it.
- The existing Dokploy project "Main" contains a compose "Docker Registry" (`registry:2`, domain via Cloudflare tunnel);
  `dokploy registry all` is empty. CI therefore parameterises the registry (`REGISTRY*` secrets) and defaults to GHCR
  as written in 08 §3.1.
- Dokploy reaches "Proxmox PVE" over SSH on its **tailnet** IP → the `tag:dokploy → tag:dokploy` SSH rule of 08 §2.1
  is mandatory before the retag (if Tailscale SSH is enabled there).

## 2. Decisions

1. **Layout follows 08 §3** (not the task wording): `deploy/compose/docker-compose.yml`, `deploy/caddy/{Dockerfile,
   Caddyfile,Caddyfile.dev}`, `deploy/compose.dev.yml`, `deploy/cloudflare/receipts-inbox/`, `deploy/env/
   production.example`, runbook `restore.md`. Service names `backend`/`dashboard` as in 08/02.
2. **Bootstrap is dry-run by default**; `--apply` executes. Read-only lookups always run, so a dry run shows the real
   IDs. Idempotent: every resource is looked up by name first; the compose file and env are re-applied on each run.
   The retag is a separate script that only prints unless `--apply --i-have-updated-the-policy`.
3. **`pg-init` one-shot service** creates the database named after `INSTANCE_NAME` (dashes → underscores) instead of
   `POSTGRES_DB=<instance>`: `POSTGRES_DB` only applies on the first init, which would break the pilot → go-live
   switch (08 §8.1). 08 §3.1 amended.
4. **Networks:** `default` (caddy, web, backend, dashboard; egress) + `db` (internal: postgres, pg-init, backend) +
   `tools` (internal: einvoice-tools, web, backend). The fork's socat proxy joins `<appName>_default`, so caddy stays
   on `default`. Postgres and the sidecar have no egress.
5. **Compose lint** (`pnpm lint:deploy`, `deploy/scripts/compose-lint.ts`, unit-tested): only `caddy` may declare
   `expose`/`ports` (exactly 443 + 8443, never `ports`), no false-looking values for the "any non-empty value enables"
   Convex flags, no `IS_TEST`, no host network/privileged/build, pinned images, backend and dashboard on the same SHA.
   Wired as a separate script (and CI job `deploy-lint`), `pnpm lint` unchanged. Adds the dev dependency `yaml` 2.9.1.
6. **Caddy**: xcaddy build of Caddy 2.11.7 + `caddy-dns/cloudflare` v0.2.4, non-root (cap_net_bind_service), the
   Caddyfile is validated during the image build. Defence in depth on top of `proxy.ts`: `app.` refuses
   `/api/v1`+`/api/mcp`; `api.` allowlists `/api/v1`, `/api/mcp`, `/api/docs`, `/api/openapi.json`, `/api/health` and
   strips `Cookie`; `convex-site.` serves only `/api/auth/*` and `/.well-known/*`; unknown hosts → 421; `:8443` only
   `api.…/api/v1`. Security headers: HSTS always, `nosniff`/`Referrer-Policy`/`X-Frame-Options`/COOP only as
   defaults (each `?header` is its own directive — in one block `?` turns into a condition for the whole block, found
   while testing). Routing was exercised locally with a test variant (internal CA, stub upstreams).
   Note for `proxy.ts`: requests on the website listener arrive with `Host: api.<BASE_DOMAIN>:8443`.
7. **einvoice-tools** is a **zero-dependency Node server** (`node:http`, Node 24 type stripping) instead of Hono
   (02 §8 amended): four routes need no framework, and the image needs no pnpm install. KoSIT 1.6.3 runs as a
   localhost daemon (`-D -G -H 127.0.0.1 -P 8081`), Mustang 2.26.0 CLI per request (concurrency 2, temp dir per call).
   Artefacts are downloaded with pinned SHA-256 (`validator-1.6.3-standalone.jar`
   `799e64be…a7c9`, `xrechnung-3.0.2-validator-configuration-2026-08-31.zip` `2530cd10…21a8`, `Mustang-CLI-2.26.0.jar`
   `42d7868c…9736`). Verified end to end on the dev machine with a temporary Temurin 17.0.20.1 JRE (not installed):
   valid fixture → acceptable, invalid → BR-DE-15 + BR-CO-16, hybrid PDF valid, PDF without XML invalid. KoSIT
   1.6.3 answers an **empty** POST with 500 (not 400 as documented) → the sidecar rejects empty bodies itself.
8. **Email Worker** test is a plain Vitest unit test with fakes (no `@cloudflare/vitest-pool-workers`, no new
   dependency); Worker types are declared locally. `wrangler deploy --dry-run` bundles it (1.8 KiB).
9. **CD** uses curl against the Dokploy tRPC API (`deploy/scripts/cd-deploy.sh`) instead of building the custom CLI
   in CI: reads the env, replaces only `*_TAG` lines, deploys, waits for the deployment by title, smoke-tests over the
   tailnet, restores the previous tags on failure. CI jobs `build-image`/`deploy` run on `main`/`v*` only and are
   opt-in via repository variables (`IMAGES_ENABLED`, `DEPLOY_ENABLED`).
10. **Server JWT JWKS**: bootstrap derives `SERVER_JWKS` (data: URI) from `JWT_PRIVATE_KEY_PEM` with
    `kid` = RFC 7638 thumbprint; the web signer must use the same `kid` derivation.
